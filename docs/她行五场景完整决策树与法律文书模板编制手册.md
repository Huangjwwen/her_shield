# 她行五场景完整决策树与法律文书模板编制手册



## **1. 文档用途**



本文档是“她行·维权导航”首版五场景决策树的法学规则底稿和文书模板编制手册，供法学、产品和开发共同使用。



本文档解决四个问题：



1. 每个场景具体问什么；

2. 用户选择不同选项后跳到哪里；

3. 满足什么条件时停止提问、进入哪个权威终点；

4. 每个终点由后端返回哪些法律文书，法学同学应如何编制、审核和交付模板。

本文中的“终点”和“裁决包”是系统内部技术概念，不表示劳动仲裁裁决、法院判决或律师出具的个案法律意见。正式页面统一称为“专属维权方案”。



## **2. 服务范围与统一入口**



首版完整支持以下五个场景：



|场景|`treeId`|节点前缀|正式终点|
|---|---|---|---|
|孕期、产期、哺乳期调岗降薪及孕产关联解除边界识别|`pregnancy_pay_cut`|`P`|`PA-PF`|
|招聘/面试性别歧视|`recruit_discrimination`|`R`|`RA-RC`|
|职场性骚扰及投诉后报复|`harassment`|`H`|`HA-HE`|
|同工同酬/晋升受限中的性别歧视|`equal_pay_promotion`|`E`|`EA-EC`|
|产假/哺乳假被拒或产假工资/生育津贴争议|`leave_benefits`|`L`|`LA-LD`|



普通违法解除、经济性裁员、合同到期不续签、一般薪资争议，以及与性别、婚育、孕产或性骚扰投诉无关的逼迫离职，不在本项目服务范围内。



统一入口选项：



- 招聘/面试性别歧视；

- 职场性骚扰；

- 孕期、产期、哺乳期被调岗降薪；

- 同工不同酬、晋升受限；

- 产假/哺乳假被拒或产假工资/生育津贴争议；

- 不确定，想先让系统帮助判断。

“不确定”入口处理：用户提交 1\-500 字描述，系统返回最多两个候选场景，由用户确认后进入对应完整子树。模型无法识别且本地关键词无匹配时进入 `OOS-unclassified`。`OOS` 和 `OOS-unclassified` 均按 OOS 规则处理：后端不返回文书，前端不展示文书区，只展示服务边界和公共求助渠道。



## **3. 决策树统一规则**



### **3.1 节点规则**



- 每个节点必须有唯一 `nodeId`、明确问题、完整选项和确定下一跳；

- 单选、多选、日期和简短文本必须分别标注类型；

- 每个选项必须指向存在的下一节点或候选终点；

- “不确定”“暂时没有证据”等选项不能成为死路；

- 风险标记只用于后续组合判断，不得单独当作法律结论；

- 前端只按配置探路，后端收到 `path + answers` 后重新执行规则并确定权威终点。

### **3.2 终点规则**



- 正式终点必须写明触发条件、行动重点、法律依据和文书白名单；

- `OOS` 不返回本项目文书；

- 时效风险终点不能直接表述为“已经过期”或“不能维权”；

- 证据不足终点应先给固定证据方案，不得因为证据少直接认定不成立；

- 存在人身安全风险时，安全提醒优先于劳动程序和文书推荐；

- 每个非 OOS 终点原则上返回 1\-3 份当前阶段最需要的文书。

## **4. 孕期、产期、哺乳期调岗降薪子树**



### **4.1 场景目标**



判断用户应先提出书面异议、进入投诉/仲裁准备、补充证据，还是优先核实时效和关联事实。



### **4.2 完整节点**



|节点|问题|选项与下一跳|标记/说明|
|---|---|---|---|
|`P1`|你现在遇到的是哪类问题？|孕期/产期/哺乳期被调岗降薪 → `P2`；其他 → 对应子树|场景入口|
|`P2`|你目前和单位的关系是？|仍在职 → `P3`；因孕产问题已离职/被口头辞退/收到解除通知 → `P4`；不确定解除是否与孕产有关 → `P4`；明确确认与孕产、性别或婚育无关 → `OOS`|不确定时标记 `relation_uncertain`，不能提前拒绝|
|`P3`|公司是否发过调岗、降薪或取消待遇的通知？|书面通知 → `P4`；明确口头通知 → `P4`；尚无正式通知但已暗示 → `P3A`|\-|
|`P3A`|公司暗示的具体内容是什么？|明确将调岗/降薪/取消待遇 → `P4`；明确要求辞职或暗示离开 → `P4`；仅称可能调整但无具体安排 → `PE`；只有态度变化或边缘化感受 → `PE`|前两项分别标记 `anticipated_action`、`anticipated_exit`|
|`P4`|这件事是否可能仍在劳动仲裁一般时效内？|措施尚未实施 → 有离职暗示时 `PF`，其余 `PE`；1 年内/不确定/超过 1 年 → `P5`|尚未实施时跳过 `P5-P7`；不确定标记 `time_uncertain`；超过一年标记 `time_risk`|
|`P5`|你现在处于哪个阶段？|孕期/产假中/哺乳期/不确定 → `P6`|\-|
|`P6`|公司已经实际采取了什么行为？|调岗/降薪或扣绩效/调岗并降薪 → `P7`；要求主动辞职/解除劳动合同 → `P8`；无法判断是否与孕产有关 → `P9`|前三项本身表示已实施；`P6.relation_uncertain` 只用于补证和措辞，不单独触发 `PF/PC`|
|`P7`|是否影响待遇、岗位级别、劳动强度、身体安全或职业发展？|工资福利降低/岗位降级或边缘化/增加不适合孕产状态的劳动/工作条件明显变差/均无明显变化 → `P8`|最后一项标记 `harm_low`，不代表合法；所有实体路径都继续询问签署风险|
|`P8`|是否签过离职、调岗、降薪或协商解除文件？|没签 → `P9`；已签但不情愿 → `P9`；主动提交过辞职 → `P9`；不确定 → `P9`|分别标记 `signed_under_pressure`、`voluntary_resignation_submitted`、`document_uncertain`；不得在此提前结束|
|`P9`|你手上有哪些证据？（多选）|聊天/邮件、工资流水、孕产证明、劳动合同/岗位说明、考勤 → `P10`；暂时没有 → `P10`|无证据标记 `evidence_weak`|
|`P10`|你已经采取过什么行动？|`P10=arbitration_started` → `PD`；**用户尚未仲裁，且（任一解除/逼迫离职边界条件成立）** → `PF`；有 `P4.time_risk` → `PC`；未行动/仅口头沟通 → 无签署风险时 `PA`、有风险时 `PB`；已内部书面投诉/已外部投诉 → `PB`|PF 条件必须实现为 `P10 != arbitration_started AND boundaryMatched`；规则优先级：已仲裁 → 服务边界 → 时效风险 → 签署风险 → 行动状态|

**边界判断指引**：只有用户明确确认解除原因与孕产、性别、婚育无关，且不存在时间顺序、单位表述或其他关联线索时，才可选择 `P2=confirmed_unrelated`。只要用户拿不准，一律按 `P2=relation_uncertain` 继续；`P2` 与 `P6` 的同名标记必须带来源节点消费，前者可触发 `PF`，后者只用于补证和谨慎措辞。



### **4.3 终点与文书**



|终点|触发条件|行动重点|后端返回文书|
|---|---|---|---|
|`PA` 未正式行动|未正式行动或仅口头沟通，且无高风险签署标记|书面提出异议，固定通知和反对意见|《调岗/降薪异议函》；《证据目录》|
|`PB` 已沟通/投诉或存在签署风险|已投诉、已签但不情愿或文件内容不明；主动提交辞职进入 `PF`|补强证据，按职责和具体请求准备材料|《证据目录》必选；监察、仲裁和恢复待遇文书按条件返回|
|`PC` 时效风险|用户选择超过 1 年|核实起算、中断、中止和连续拖欠等情形|《法律援助咨询问题清单》；《证据目录》|
|`PD` 已仲裁|已申请劳动仲裁|补充证据、庭前陈述和后续期限提醒|《劳动仲裁补充材料清单》；《证据目录》|
|`PE` 尚无明确措施|只有模糊暗示、态度变化，或措施尚未实施且无离职暗示|固定原话、时间、参与人及现岗位待遇|《证据目录》|
|`PF` 孕产关联解除/离职边界|尚未仲裁，且因孕产问题离职、被辞退、收到解除通知或被要求主动辞职|只固定孕产关联、解除/离职文件和沟通时间线；不判断违法解除|仅《证据目录》；不生成法援问题、解除、赔偿、时效、仲裁或调岗降薪文书|

## **5. 招聘/面试性别歧视子树**



### **5.1 完整节点**



|节点|问题|选项与下一跳|说明|
|---|---|---|---|
|`R1`|歧视发生在哪个环节？|招聘广告/岗位要求、面试提问 → `R2`；取消 offer、投简历后被拒 → `R3`|\-|
|`R2`|是否明确提到性别、婚育、怀孕或生育计划？|明确提到/暗示或追问 → `R4`；没有，只是感觉不公平 → `R5`|\-|
|`R3`|是否已经出现不利结果？|未进入面试/未被录用/offer 被取消或降低待遇 → `R2`；还没有结果 → `RA`|不利结果不得跳过性别、婚育关联询问|
|`R4`|你有哪些证据？（多选）|招聘广告截图、聊天/邮件、录音/面试记录、拒录通知 → `R6`；暂无 → `RA`|暂无证据标记 `evidence_weak`；录音提醒限本人参与对话|
|`R5`|是否有可对比信息？|同岗位男性被正常推进/公司长期限制女性 → `R6`；暂无 → `RA`；用户明确核对为非性别婚育原因 → `OOS`|`confirmed_unrelated` 不得由系统推断|
|`R6`|你希望先走哪种方式？|要求企业说明/向平台投诉/了解就业歧视民事诉讼 → `RB`；向人社或劳动监察反映 → `RC`；只整理材料 → `RA`|到达候选终点后提交后端裁决|



### **5.2 终点与文书**



|终点|触发条件|行动重点|后端返回文书|
|---|---|---|---|
|`RA` 证据固定|尚无结果、证据不足或只整理材料|保存招聘原文、沟通记录、时间线和拒录材料|《证据目录》|
|`RB` 企业/平台沟通或民事咨询|要求企业说明、向平台投诉或了解就业歧视民事诉讼|书面询问录用标准、提交歧视线索或准备民事咨询材料|《证据目录》必选；平台投诉才返回《招聘歧视投诉说明》；要求企业说明且确有投递/面试经历时返回《要求说明不予录用原因函》；民事咨询和纯广告说明路径不返回不匹配函件|

## **6. 职场性骚扰及投诉后报复子树**



### **6.1 完整节点**



|节点|问题|选项与下一跳|说明|
|---|---|---|---|
|`H1`|对方行为主要是哪一类？|言语/黄色玩笑、文字图片或聊天骚扰 → `H2`；肢体接触、利益交换性要求、跟踪威胁 → `H3`|\-|
|`H2`|你是否表达过拒绝或不舒服？|明确拒绝后仍继续/表达不适后仍继续 → `H4`；尚未表达 → `H5`|不以是否拒绝作为性骚扰成立的唯一条件|
|`H3`|现在是否存在紧急人身安全风险？|是 → `HC`；否 → `H4`|安全终点优先|
|`H4`|行为人身份是谁？|直属上级、普通同事、客户/合作方、不确定 → `H4A`|记录是否掌握考核权|
|`H4A`|在当前安全状态下，你希望先走哪条路径？|先固定证据 → `HA`；向单位投诉 → `H6`；向有关国家机关投诉或报案咨询 → `HD`；了解民事救济 → `HD`|后两项分别标记 `external_state_route`、`civil_route`|
|`H5`|你希望先怎么做？|固定证据/需要拒绝话术 → `HA`；正式投诉 → `H6`|\-|
|`H6`|公司是否有处理或投诉渠道？|有 HR/合规/工会、没有明确渠道 → `H7`；已投诉但公司不处理 → `HD`|\-|
|`H7`|你有哪些证据？（多选）|聊天/图片、录音录像、证人、事后记录、暂时没有 → `H8`|暂无证据标记 `evidence_weak`；证据弱不阻断投诉|
|`H8`|已采取哪些行动，公司是否作出不利处理？|未投诉/等待内部处理 → `HB`；公司不处理或包庇/已外部求助 → `HD`；投诉后有不利对待 → `H8A`|不利对待标记 `retaliation`|
|`H8A`|投诉后的不利对待达到什么程度？|态度变化、排挤、冷处理 → `HD`；实际调岗降薪、扣绩效、处分 → `HE`；要求辞职、解除或妨碍工作 → `HE`；跟踪威胁或人身风险 → `HC`；无法判断或均不符合 → `HD`|分别标记轻度、实质、退出、安全或未分级报复风险；兜底项不得中断路径|



### **6.2 终点与文书**



|终点|触发条件|行动重点|后端返回文书|
|---|---|---|---|
|`HA` 证据固定/拒绝表达|暂未投诉或证据弱|固定证据、准备拒绝表达、避免单独接触|《证据目录》|
|`HB` 内部投诉|准备或已经内部投诉|请求启动调查、保护投诉人、禁止报复|《证据目录》必选；首次投诉只返回《性骚扰内部投诉说明》，已提交并等待处理时只返回《要求公司启动调查处理函》，两份函件不得同时返回|
|`HC` 安全优先|存在人身安全、威胁、跟踪或肢体风险|离开危险环境、联系可信任人员，必要时报警|《紧急求助记录清单》；《证据目录》|

|`HE` 投诉后实质报复|实际调岗降薪、扣绩效、处分、要求离职或妨碍工作|固定“投诉在先、不利处理在后”的完整时间线，区分人格权与劳动争议请求|默认《要求公司启动调查处理函》、《证据目录》；仅实际调岗降薪、绩效或处分且存在可量化劳动请求时附仲裁要点；要求离职/解除路径不生成解除或仲裁文书|

## **7. 同工同酬/晋升受限子树**



### **7.1 完整节点**



|节点|问题|选项与下一跳|说明|
|---|---|---|---|
|`E1`|差异待遇主要体现在哪里？|基本工资、奖金绩效、晋升职称、培训项目 → `E2`|\-|
|`E2`|是否有具体可比较对象或比较范围？|同岗同工、同级近似工作、同批晋升候选 → `E3`；只有感觉/信息不足 → `E3A`|后两项标记 `comparison_weak`，由过渡节点厘清独立关联线索|
|`E3`|岗位职责、工作量、绩效、资历和任职条件是否大体可比？|大体可比/存在已知客观差异/不确定 → `E4`|后两项分别标记 `objective_difference_present`、`comparability_uncertain`|
|`E3A`|没有明确比较对象时，是否有直接性别/婚育表述或时间、模式线索？|有直接性别表述/婚育表述/时间或模式线索 → `E5`；只有感受/不确定 → `EA`|前三项标记 `gender_link_clue`，后两项先补事实|

## **10. 法学同学如何编制文书模板**



### **10.1 每份模板的必交内容**



每份模板不是只交一段 Word 正文，而应提交一个完整“模板包”：



1. 模板元数据；

2. 可直接使用的基准正文；

3. 必填字段和选填字段清单；

4. 条件段落及其触发条件；

5. 附件和证据提示；

6. 适用终点和禁用终点；

7. 正文如直接引用法规名称或条款号，由法学同学写入自然语言正文，并附“引用核对注记”；该注记不控制裁决包法律依据；

8. 使用风险、免责声明和不适用情形；

9. 至少两组完整示例数据及预期成文结果；

10. 版本号和审核日期。

### **10.2 模板元数据表**

### **10.3 正文编写结构**



函件类文书建议按以下顺序编写：



1. 标题；

2. 致送对象；

3. 当事人和劳动关系基本信息；

4. 已确认事实，按时间顺序陈述；

5. 对相关安排的态度或异议；

6. 具体、可执行且不过度扩张的请求事项；

7. 请求书面回复及合理期限；

8. 附件目录；

9. 姓名和日期；

10. “请核对事实后使用”的提示。

清单类文书建议按“事项、已有材料、缺失材料、取得方式、原件位置、提交状态、备注”组织，不写成大段法律分析。



### **10.4 字段设计规则**



- 字段必须来自用户已确认的结构化答案或提交裁决前的补充表单；

- 禁止让模型猜测姓名、日期、金额、公司行为、证人和沟通原话；

- 必填字段缺失时，后端返回 `MISSING_DOCUMENT_FIELDS`，不得生成半成品；

- 选填字段缺失时，应删除整句或使用法学审核过的中性表达，不能留下语病；

- 选填字段所在句子必须单独标注 `[字段条件：fieldName 已填写]`；多个字段共同决定一段时写“均已填写”或“任一已填写”，分别表示全部有值或至少一个有值，不能把选填占位符直接放入固定段落；

- 同一含义只使用一个字段名，例如统一使用 `companyName`，不要混用 `employer`；

- 日期统一为 `YYYY-MM-DD`，金额字段必须同时标注单位；

- 自由文本字段必须设置长度上限，并注明可接受内容。

建议的通用字段：



```Plain Text
userName, companyName, position, employmentStartDate,
eventDate, noticeDate, communicationTarget,
currentSalary, changedSalary, requestedReplyDate,
evidenceItems, generatedDate
```



上述字段只用于填入文书正文。决定条件段落是否出现时，不使用 `noticeType`、`eventStage`、`harmType` 等另行抽象的字段，统一使用 10\.5 节定义的节点 ID 条件。



### **10.5 条件段落规则**



法学同学应把不同情形写成独立条件段落，不要把所有可能性塞进同一正文。条件直接引用决策树节点 ID 和该节点的技术选项值，禁止另造 `noticeType`、`eventStage`、`harmType` 等中间条件字段。

字段存在条件只控制选填内容是否成文，不参与终点裁决，也不替代节点条件。例如：

```text
[字段条件：replyDeadline 已填写]
请于{{replyDeadline}}前书面回复。
```

字段为空时后端省略整个段落；不得输出空占位符，也不得调用模型补值。

同一段落前连续标注节点条件和字段条件时，两者按“且”合并。例如先标注 `[条件：H7 包含 witness]`，再标注 `[字段条件：witnesses 已填写]`，只有路径命中且用户填写证人信息时才渲染该段。



#### **10.5.1 统一条件语法**



单选节点：



```JSON
{ "node": "P3", "value": "oral" }
```



含义：用户在 `P3` 选择了技术值 `oral`。



多选节点包含某一项：



```JSON
{ "node": "P9", "contains": "chat_email" }
```



多选节点包含任一项：



```JSON
{ "node": "P9", "containsAny": ["chat_email", "payroll"] }
```



来源节点产生了某个标记：



```JSON
{ "node": "P8", "flag": "signed_under_pressure" }
```



组合条件：



```JSON
{
  "all": [
    { "node": "P3", "value": "oral" },
    { "node": "P8", "flag": "signed_under_pressure" }
  ]
}
```



```JSON
{
  "any": [
    { "node": "P6", "value": "salary_reduced" },
    { "node": "P6", "value": "both" }
  ]
}
```



约束：



- `node` 必须是当前模板适用树中真实存在的节点 ID；

- `value/contains/containsAny` 必须使用下表登记的技术值；

- `flag` 必须使用 10\.5\.7 标记索引中的值，并写明产生它的来源节点；

- 单选用 `value`，多选用 `contains` 或 `containsAny`，不能混用；

- 多选节点中的 `none` 与其他证据值互斥，后端和前端都必须拒绝同时选择；

- 条件索引是法学、树配置和模板共同使用的唯一词表；技术值变更必须提升树版本并同步检查所有模板。

### **10.6 法律依据写法**



这里必须区分“文书正文的自然语言引用”和“裁决包法律依据区的控制逻辑”：



1\. **文书正文可以自然引用法规。** 法学同学可以直接写“根据《女职工劳动保护特别规定》第五条……”等成文内容，该句属于文书正文，由法学同学负责准确性，开发应按审核稿忠实渲染；

2\. **引用核对注记只用于交接审核。** 正文引用法规时，在正文段落后或 \`legalCitationNotes\` 中另写 \`\[引用核对：female\_worker\_protection\_5\]\`。开发据此检查该依据键是否已在当前终点的法律依据映射中登记，但该注记不进入用户成文、不参与条件判断，也不能转换成模板的 \`legalBasisKeys\`；

3\. **裁决包法律依据区完全独立。** 其中展示哪些法条、展示顺序、条件法条、\`displayText/fullText\` 和官方链接，只由第 11 章法律依据库及 11\.10 的终点法律依据映射控制，文书正文是否引用某条法规不自动增加或删除裁决包法条；

4\. **发现不一致必须退回法学确认。** 正文引用键未登记、条款名称不一致或终点映射缺失时，开发只能形成校验问题，不能自行修改正文、补录法条或猜测映射。



示例：



```Plain Text
根据《女职工劳动保护特别规定》第五条，用人单位不得因女职工怀孕、生育、哺乳降低其工资。
[引用核对：female_worker_protection_5]
```



其中第一行进入成品文书，第二行只进入转换差异报告和审核记录。



### **10.7 禁止性表达**



模板正文和使用说明不得出现：



- “保证胜诉”“一定胜诉”“仲裁一定支持”；

- 未经事实核验的“公司肯定违法”“文件当然无效”；

- 把一般仲裁时效机械写成“超过一年必然不能处理”；

- 暗示用户删除、修改、伪造证据；

- 鼓励窃听、侵入设备或其他违法取证方式；

- 超出本项目范围的违法解除专门结论；

- 模型补写的未确认事实。

### **10.8 法学与开发交付物清单**



每一份法律文书模板都采用同一交接方式：**法学同学交付 3 份业务材料，开发同学完成 5 项技术工作。** 法律依据条目和终点映射不属于文书模板交付物，统一按 11\.10 单独交接。



法学同学不负责手写 JSON，也不实现渲染代码；法学交付自然语言正文、`{{字段}}` 和 `[条件：节点ID = 技术值]`。开发负责忠实转换，不能擅自增删法律内容、改写条件含义或补造字段来源。

|`applicableTerminals`|允许使用该模板的权威终点|
|`purpose`|文书解决的问题、使用阶段和预期作用|
|`requiredFields`|缺少时不能生成成品文书的字段|
|`optionalFields`|缺少时可以删除对应句子或段落的字段|
|`conditionalRequiredFields`|仅当某条件段落入选时必须提供的字段及其条件|
|`warnings`|使用前必须展示的事实核对、送达、证据等提醒|
|`conditionIndexVersion`|编制时使用的 10\.5 条件索引版本|



法学同学提交前需要确认：`documentKey`、场景和终点已在文书映射表中登记，不能由开发自行猜测。



#### **10.8.2 法学材料二：带条件标记的自然语言正文**



正文用 `{{字段名}}` 标记需要后端填入的动态内容，用独立的 `[条件：...]` 行标记下一段的出现条件。



```Plain Text
文书名称：调岗/降薪异议函

致：{{companyName}}

本人{{userName}}于{{eventDate}}获知相关安排。

[条件：P3 = oral（明确口头通知）]
上述安排系口头告知，现请求贵司书面确认具体内容及依据。

[条件：P3 = written（书面通知）]
本人已于{{noticeDate}}收到贵司书面通知。

[条件：P8 标记 signed_under_pressure（已签但不情愿）]
本人同时说明，相关文件的签署背景及真实意思表示仍需结合当时沟通过程核实。

现就上述安排正式提出异议，请求贵司书面说明具体内容及依据。

{{userName}}
{{generatedDate}}
```



正文编写要求：



- 条件必须使用 10\.5 已登记的节点 ID、技术值和标记；

- 一个条件控制一个完整段落，不把条件标记插在句子中间；

- 多条件使用清楚的自然语言，例如 `[条件：P6 = salary_reduced 或 P6 = both]`；

- 同时满足使用“且”，任一满足使用“或”，开发分别转换为 `all`、`any`；

- 条件段落不出现时，前后固定段落仍须语义和格式完整；

- 对口头通知与书面通知等互斥条件段落，法学同学必须在材料二中使用自然语言单独声明互斥组，例如 `[互斥组：通知形式；段落：书面通知事实、口头通知事实；要求：最多出现一段]`；

- 每个互斥组中的段落应有可识别名称。法学同学不写 JSON，开发根据该声明分配稳定 `blockId` 并转换为 `mutuallyExclusiveGroups`；未声明清楚时退回确认，开发不能自行猜测。

#### **10.8.3 法学材料三：字段来源说明**



字段来源分为三类：裁决前由用户补充的 \`documentFields\`、系统字段、决策树节点答案。**\*\*节点答案主要用于条件判断；需要进入正文的姓名、日期、金额等内容原则上通过结构化 \`documentFields\` 单独收集。\*\***



|字段名|类型|必填|数据来源|校验要求|
|---|---|---|---|---|
|`companyName`|`string`|是|文书字段表单由用户填写|长度限制，去除控制字符|
|`userName`|`string`|是|文书字段表单由用户填写|长度限制，纯文本转义|
|`eventDate`|`date`|是|文书字段表单由用户确认|`YYYY-MM-DD`|
|`noticeDate`|`date`|条件必填|文书字段表单由用户填写；当 `P3 = written` 的段落入选时必填|`YYYY-MM-DD`，不得从 `P3` 猜测|
|`communicationTarget`|`string`|否|文书字段表单由用户填写|长度限制，纯文本转义|
|`generatedDate`|`date`|是|后端生成|使用服务器日期并固定格式|



特别说明：`P3` 只回答通知形式是 `written/oral/implied`，不包含通知日期。因此 `eventDate`、`noticeDate` 不能标为“来自 P3 节点回答”。如果未来新增日期节点，应使用该真实节点 ID，并提升条件索引和树版本。



法学同学还应说明：



- 每个选填字段缺失时应删除哪句话或采用什么中性替代文本；

- 字段是否只在特定条件段落中使用；

- 金额、日期和附件编号的格式；

- 是否含个人敏感信息及是否真的有必要收集。

#### **10.8.4 开发工作一：接收校验**



开发收到三份材料后，先生成校验报告，不应直接开始转换。至少检查：



- `documentKey` 是否存在于终点到文书映射表；

- `applicableTreeIds/applicableTerminals` 是否真实存在且相互匹配；

- 每个 `requiredField/optionalField` 是否有唯一、明确的数据来源；

- 正文中的每个 `{{字段}}` 是否在字段来源表登记；

- 每个条件节点、技术值和标记是否存在于指定版本的 10\.5 条件索引；

- 法学声明的每个互斥段落名称是否都能唯一对应一个条件段落；

- 条件段落是否可能同时触发并产生冲突内容；互斥声明缺失、名称不明确或无法证明不会同时出现时均不得转换发布。

校验失败时将问题退回法学同学确认，开发不得自行修正法律内容。



#### **10.8.5 开发工作二：转换为 JSON 配置**



开发在不改变正文和条件含义的前提下，将三份材料转换为版本化 JSON：



```JSON

  "applicableTerminals": ["PA"],
```

每个 `bodyBlock` 必须有稳定 `blockId` 和确定 `order`，便于测试、审计和法学核对。开发根据法学材料二的 `[互斥组：...]` 声明生成 `mutuallyExclusiveGroups`；`cardinality: at_most_one` 表示组内最多渲染一段。模板只允许使用已定义字段和有限条件，不允许嵌入 JavaScript、任意表达式或可执行代码。



#### **10.8.6 开发工作三：实现条件渲染逻辑**



后端只能使用重放决策树得到的 `canonicalNodeAnswers` 和带来源节点的 `canonicalFlags`，不得信任客户端提交的 `flags`。



```JavaScript
function renderDocument(template, canonicalNodeAnswers, canonicalFlags, documentFields) {
  const context = {
    nodeAnswers: canonicalNodeAnswers,
    flags: new Set(canonicalFlags.map(item => `${item.node}:${item.flag}`))
  };

  return template.bodyBlocks
    .slice()
    .sort((a, b) => a.order - b.order)
    .filter(block => block.type === 'fixed' || checkCondition(block.when, context))
    .map(block => replacePlaceholdersEscaped(block.text, documentFields))
    .join('\n\n');
}
```



`checkCondition` 必须实现 10\.5 约定的 `{node,value}`、`{node,contains}`、`{node,containsAny}`、`{node,flag}`、`all` 和 `any`，不能允许模板执行任意代码。



#### **10.8.7 开发工作四：实现字段校验**



生成文书前必须：



1. 检查所有 `requiredFields` 是否有非空合法值；

2. 检查实际入选段落所引用的条件必需字段，例如书面通知段落中的 `noticeDate`；

3. 对字符串、日期、金额、附件编号分别执行类型和格式校验；

4. 对所有插值内容进行纯文本转义；

5. 检查成品中是否残留未替换的 `{{字段}}`；

6. 缺少字段时返回 `MISSING_DOCUMENT_FIELDS` 和具体字段路径，不生成半成品；

7. 用户补充字段并重新调用 `resolve` 后，重新执行后端路径复算、条件判断和字段校验。

#### **10.8.8 开发工作五：提交法学核验**



开发转换完成后，应按条件组合生成文书快照并交回法学同学。至少核对：



- 固定正文是否与法学原稿逐字一致；

- 字段替换是否来自正确来源；

- 条件段落在应出现时出现、不应出现时省略；

- 互斥段落不会同时出现；

- 格式、换行、落款和附件是否正常；

- 缺失字段是否正确阻断半成品；

- 模型关闭或失败时仍能生成确定性文书。

法学同学确认后填写模板审核记录，开发才能将 `reviewStatus` 从 `reviewing` 改为 `published`。任何正文或条件修改都应重新生成快照并复核。



#### **10.8.9 一句话职责边界**



|角色|交付内容|
|---|---|
|法学同学|元数据表、带条件标记的自然语言正文、字段来源说明，共 3 份材料|
|开发同学|接收校验、转换 JSON、实现条件渲染、实现字段校验、提交法学核验，共 5 项工作|



**法学同学不写 JSON；开发同学不擅改法律内容。最终发布物必须由法学自然语言原稿、技术 JSON 配置和渲染快照三方互相对应。**



## **11. 法律依据库建设规范**



### **11.1 法律依据库的定位**



法律依据库不是法规百科、链接收藏夹或 AI 摘要库。库中只保存：



> 与五个服务场景及具体权威终点直接相关，并且最终会出现在裁决包“法律依据”区域中的法条原文。
> 
> 



因此，一条法律依据只有同时满足以下条件才可入库：



1. 与至少一个 `treeId` 的具体法律问题直接相关；

2. 被至少一个正式 `terminalId` 或经审核的条件分支引用；

3. 来源于官方、可追溯的现行法律文本；

4. 已录入法规名称、条款号和完整法条原文；

5. 已由法学同学核对原文、版本和适用范围；

6. 后端能够通过 `legalBasisKey` 将其放入对应裁决包。

不应入库的内容：



- 与五个场景没有直接关系的泛化法条；

- 仅供法学同学研究、但不会展示给用户的案例笔记；

- 新闻、公众号文章、律师解读或搜索结果摘要；

- AI 生成或改写的所谓“法条内容”；

- 只有法规名称或网页链接、没有法条原文的空记录；

- 已失效但未标明历史状态的条文；

- 没有任何终点引用的“备用知识”。

研究笔记、典型案例和内部解释可以另建“法学审核资料库”，但不得混入用户可见的法律依据库。



### **11.2 建库方式：先终点，后法条**



法律依据库应从决策树终点倒推建设，不建议先收集大量法规再寻找使用场景。



每棵树按以下顺序处理：



1. 列出该树全部正式终点；

2. 写清每个终点向用户输出的行动建议和文书；

3. 提炼支撑这些输出的具体法律问题；

4. 检索对应的现行法律、行政法规、部门规章或地方规定；

5. 从官方文本中定位具体条款；

6. 将完整法条原文录入法律依据库；

7. 建立 `treeId + terminalId -> legalBasisKeys` 映射；

8. 用测试路径生成裁决包，确认展示的原文与当前路径真正相关；

9. 删除没有终点引用或只起背景作用的冗余条目。

示意关系：



```Plain Text
场景树 -> 权威终点 -> 当前法律问题 -> legalBasisKeys -> 法律依据库原文 -> 裁决包法律依据区
```



例如，法学同学不能因为某部法律整体与女性权益有关，就把整部法律加入某个终点。应当先确认该终点涉及的是招聘条件、孕产期待遇、单位防治性骚扰义务、劳动争议时效还是其他具体问题，再选择直接相关的条款原文。



### **11.3 每条法律依据的数据结构**



每一条记录原则上对应一个明确条款；同一条款包含多款、多项且需要整体理解时，可作为一条记录完整保存。



|字段|是否必填|法学填写要求|
|---|---|---|
|`legalBasisKey`|是|稳定唯一键，建议使用“法规简称 \+ 条款号 \+ 必要项号”|
|`lawName`|是|法规官方全称，不使用民间简称代替|
|`documentNumber`|建议|主席令、国务院令或其他官方文号|
|`issuer`|是|制定或公布机关|
|`article`|是|条、款、项定位，例如“第四十八条第二款”|
|`fullText`|是|该条款经核对的完整法条原文，不得改写|
|`displayText`|是|默认展示的原文；应等于 `fullText` 或其中连续、完整的原文段落|
|`officialUrl`|是|可直接核验原文的官方页面或官方 PDF|
|`effectiveDate`|是|当前文本生效日期|
|`status`|是|`draft/reviewing/published/retired`|
|`treeIds`|是|直接相关的场景列表|
|`terminalIds`|是|会在裁决包中引用该条文的终点列表|
|`issueTags`|是|具体法律问题标签，不使用宽泛标签|
|`applicabilityNote`|是|供后端选择和法学审核使用，不作为法条原文展示|
|`regionalScope`|是|`national` 或具体地区；地方规定必须注明地区|
|`retrievedAt`|是|从官方来源核验的日期|
|`reviewedBy`|是|法学审核人|
|`reviewedAt`|是|审核日期|
|`version`|是|本条库记录版本号|
|`supersedes`|否|替代的旧记录键或版本|

### **11.4 法条原文录入规则**



- `fullText` 必须从官方来源逐字核对录入，保留原有条、款、项顺序；

- 不得把法学同学的概括、产品说明或模型摘要写入 `fullText`；

- 不得为了“更好懂”擅自替换法律术语；

- 原文中的标点、数字、主体和限定条件都应核对；

- 条文引用其他条款且不读取会造成误解时，应同时建立被引用条款记录，并在 `relatedLegalBasisKeys` 中关联；

- 官方页面与 PDF 内容不一致时，暂停发布，由法学同学确认现行有效文本；

- 地方规定必须记录适用地区，后端只有在用户地区已确认且规则允许时才能返回；

- 同一法条被多个场景使用时只存一份原文，通过 `treeIds/terminalIds` 建立多对多映射。

### **11.5 裁决包展示规则**



后端复算权威终点后，根据 11\.10 的独立“终点法律依据映射”取得必选依据和满足条件的依据键，再从法律依据库读取 `published` 记录并组装裁决包法律依据区。前端树投影、文书模板和终点基础配置均不得自行决定该区域展示哪些法条。



每条用户可见法律依据至少展示：



1. 法规官方全称；

2. 条、款、项；

3. `displayText` 法条原文；

4. “查看完整条文”入口，对应 `fullText`；

5. 官方来源链接；

6. 生效状态或核验日期。

展示约束：



- 默认展示与当前路径最直接相关的 1\-2 条，其他已映射条文放入“更多法律依据”；

- `displayText` 必须是法条原文，不能展示 AI 改写后再标成“原文”；

- 原文较长时，可以默认折叠，但用户必须能在当前页面展开 `fullText`；

- 如截取连续款项作为 `displayText`，应使用省略标记并明确存在完整条文，不得拼接不连续句子形成新含义；

- `applicabilityNote` 是内部说明，不与法条原文混排；如需用户说明，应使用单独的“与当前情况的关系”字段，并明确它不是法条原文；

- AI 只能润色“与当前情况的关系”，不能选择、修改、概括或补写法条原文；

- `OOS` 和 `OOS-unclassified` 不返回本项目终点法律依据，只返回服务边界和公共求助渠道。

裁决包建议结构：



```JSON
{
  "legalBasis": [
    {
      "legalBasisKey": "example_law_article_x",
      "lawName": "法规官方全称",
      "article": "第X条第X款",
      "displayText": "经审核、默认展示的连续法条原文",
      "fullText": "经审核的完整法条原文",
      "officialUrl": "https://官方来源",
      "effectiveDate": "YYYY-MM-DD",
      "retrievedAt": "YYYY-MM-DD",
      "relationToCase": "单独展示的路径关联说明，不属于法条原文"
    }
  ]
}
```



### **11.6 终点映射表怎么做**



法学同学应为每个终点提交一行映射，不允许开发根据关键词自行关联法条：



|`treeId`|`terminalId`|当前法律问题|必选 `legalBasisKeys`|条件 `legalBasisKeys`|不应展示的依据|
|---|---|---|---|---|---|
|`pregnancy_pay_cut`|`PA`|孕产期调岗降薪异议、书面确认|由法学同学填写|根据调岗/降薪/劳动安排标记选择|与当前事实无关的解除条款|
|`harassment`|`HC`|人身安全和紧急求助|由法学同学填写|根据行为类型选择|普通薪资争议条款|



映射审核重点：



- 同一终点在不同风险标记下，是否需要增加或移除某条依据；

- 终点行动建议和文书请求是否都能在映射条文中找到直接支撑；

- 是否因为“看起来专业”展示了与当前路径无关的条文；

- 是否遗漏条文中的限制、例外、适用主体或地区条件；

- 条文是否会让用户误以为系统已经完成个案违法认定。

### **11.7 建库与审核流程**



1. 场景负责人提交“终点—法律问题—候选条款”表；

2. 法学同学只从官方来源取得现行文本；

3. 录入人填写完整字段并保存为 `draft`；

4. 法学负责人完成原文核验：逐字比对 `fullText`、条款号、效力状态和官方来源；

5. 法学负责人完成适用性复核：检查终点关联、条件规则、排除情形和裁决包展示必要性，并分别留下两项检查记录；

6. 开发执行 Schema、URL、空字段和引用完整性校验；

7. 系统为每个终点生成裁决包快照；

8. 法学负责人检查用户实际看到的法条原文、顺序和展开内容；

9. 审核通过后改为 `published`；

10. 未被任何已发布终点引用的记录不得随首版发布。

### **11.8 更新、失效与历史结果**



- 法律修订、废止、司法解释变化或官方勘误时，创建新版本，不直接覆盖旧原文；

- 新版本审核通过后，将旧版本标记为 `retired`，并填写 `supersedes`；

- 新裁决只读取 `published` 且在当前日期有效的记录；

- 已保存历史裁决包保留生成时的法条原文快照和依据库版本，不自动改写；

- 用户查看旧结果时，应提示依据版本可能已更新，并提供“按最新规则重新评估”；

- 定期按场景复核，至少记录复核日期、复核人和是否需要更新；

- 官方来源失效、链接无法核验或有效状态不明确时，该记录不得继续用于新裁决。

### **11.9 法律依据库验收清单**



* [ ] 每条记录至少被一个正式终点引用；

* [ ] `fullText` 是从官方来源核对的完整法条原文；

* [ ] `displayText` 是完整原文或连续原文段落，没有改写和拼接；

* [ ] 法规名称、文号、条款号、公布机关和生效日期准确；

* [ ] 官方链接可以直接核验对应原文；

* [ ] 场景、终点和问题标签映射准确；

* [ ] 地方性依据标注适用地区；

* [ ] 裁决包默认只展示当前路径最相关的依据；

* [ ] 用户可以展开查看 `fullText`；

* [ ] AI 无权修改、替换或选择法条原文；

* [ ] OOS 终点不返回本项目法律依据；

* [ ] 历史版本可追溯，修订后不会覆盖旧裁决快照；

* [ ] 五棵树的每个正式终点都完成法律依据区快照验收。

### **11.10 法学与开发交付物清单**



法律依据库采用与文书模板类似、但相互独立的交接方式：**法学同学交付 2 份材料，开发同学完成 4 项工作。**



法学同学负责法条原文、适用范围、终点映射和条件规则，不需要手写 JSON 或实现后端查询代码；开发同学负责校验、结构化转换、建立索引和实现查询，不得自行补充法条原文、缩写 `displayText` 或猜测终点映射。



#### **11.10.1 法学材料一：法律依据条目表**



法学同学按 11\.3 的数据结构，为每条需要入库且会展示在裁决包中的法条填写条目表。同一法条原文只录入一次，通过材料二关联不同场景和终点。



|字段|填写说明|示例|
|---|---|---|
|`legalBasisKey`|稳定唯一键，建议“法规简称\_条款号”|`female_worker_protection_5`|
|`version`|该条库记录的独立版本号|`1.0.0`|
|`lawName`|法规官方全称|《女职工劳动保护特别规定》|
|`documentNumber`|官方文号，如无则明确填写“无”|中华人民共和国国务院令第619号|
|`issuer`|制定或公布机关|国务院|
|`article`|准确到条、款、项的定位|第五条|
|`fullText`|从官方来源逐字核对的完整法条原文，不缩写、不改写|由法学同学录入完整原文|
|`displayText`|裁决包默认显示的原文；原则上等于 `fullText`，需要缩短时只能使用连续原文段落|由法学同学明确指定|
|`officialUrl`|可直接核验该条原文的官方页面或 PDF|官方来源 URL|
|`effectiveDate`|当前文本生效日期|`YYYY-MM-DD`|
|`regionalScope`|`national` 或具体省市地区|`national`|
|`issueTags`|具体法律问题标签|`pregnancy_pay_protection`|
|`retrievedAt`|从官方来源核验的日期|`YYYY-MM-DD`|
|`applicabilityNote`|供审核和后端定位使用的适用/排除说明，不作为法条原文展示|说明适用场景及不应使用的情况|
|`status`|初始统一填写 `draft`|`draft`|



录入要求：



- 法条原文、法规名称、条款号、文号和生效日期必须以官方现行文本为准；

- `displayText` 也由法学同学提供，开发不得自行截短；

- `displayText` 如小于 `fullText`，必须是连续原文，不得拼接不连续语句；

- 图片扫描件应先人工核对文字，不能仅依赖 OCR 直接发布；

- 材料一不重复填写 `treeIds/terminalIds`，这些关系由材料二转换生成。

#### **11.10.2 法学材料二：终点法律依据映射表**



法学同学为每个正式终点指定必选和条件法律依据。映射表中的 `legalBasisKey` 必须已在材料一中录入。



|`treeId`|`terminalId`|必选 `legalBasisKeys`|条件 `legalBasisKeys`|条件规则|展示顺序|不应展示的依据|
|---|---|---|---|---|---|---|
|`pregnancy_pay_cut`|`PA`|`female_worker_protection_5`|`women_rights_48`|`P6 = salary_reduced` 或 `P6 = both`|必选依据在前|与当前事实无关的解除条款|
|`pregnancy_pay_cut`|`PC`|`labor_dispute_arbitration_27`|无|无|时效依据优先|与当前时效问题无关的实体条款|
|`harassment`|`HB`|`women_rights_25`、`civil_code_1010`|无|无|单位义务依据在前|普通薪资争议条款|



上表中的键、法规和条款仅用于展示交付格式，正式发布前必须按照材料一和官方现行文本逐项核验。



条件规则要求：



- 直接使用 10\.5 的节点条件语法，不写 `noticeType` 等抽象字段；

- 单选使用 `{node,value}`，多选使用 `{node,contains/containsAny}`，标记使用 `{node,flag}`；

- “且/或”条件分别转换为 `all/any`；

- 每个正式终点原则上至少有一条必选依据；确有例外时必须在审核报告中说明；

- `OOS/OOS-unclassified` 不填写本项目法律依据映射；

- 法学同学必须明确“不应展示的依据”，用于检查过度展示和错误复用。

#### **11.10.3 开发工作一：校验法学材料**



开发收到两份材料后先生成校验报告，不直接开始转换：



- 检查每个 `legalBasisKey + version` 是否唯一；

- 检查必填字段、日期格式、状态值和地区值是否合法；

- 检查 `fullText/displayText` 是否为空，是否包含“AI 生成”“摘要”“仅供参考”等明显非原文标志；

- 检查 `displayText` 是否等于 `fullText` 或能在 `fullText` 中找到连续匹配；

- 检查 `officialUrl` 是否可访问、是否属于官方来源允许列表，并记录核验时间；

- 检查终点映射中的 `treeId/terminalId` 是否存在；

- 检查映射中的每个 `legalBasisKey` 是否都在材料一中存在；

- 检查条件节点、技术值、标记和语法是否符合 10\.5 的指定版本；

- 检查每个正式终点是否至少有一条必选依据，或具有经法学批准的例外说明；

- 检查同一法条是否被重复录入成多个不同键；

- 检查未被任何终点引用的条目，首版不得发布无引用条目。

自动校验只能发现结构和明显异常，不能代替法学同学逐字核对官方原文。校验失败时退回法学同学确认，开发不得自行修正文号、法条原文、适用说明或缺失映射。



#### **11.10.4 开发工作二：转换为版本化 JSON**



开发将校验通过的条目表转换为后端法律依据记录。以下仅为结构示例，法律内容和日期发布前仍须法学复核：



```JSON
{
  "legalBasisKey": "female_worker_protection_5",
  "version": "1.0.0",
  "lawName": "女职工劳动保护特别规定",
  "documentNumber": "中华人民共和国国务院令第619号",
  "issuer": "国务院",
  "article": "第五条",
  "fullText": "由法学同学从官方现行文本逐字核对录入的完整法条原文",
  "displayText": "由法学同学指定的完整原文或连续原文段落",
  "officialUrl": "https://官方来源地址",
  "effectiveDate": "YYYY-MM-DD",
  "status": "reviewing",
  "issueTags": ["pregnancy_pay_protection"],
  "applicabilityNote": "适用与排除范围说明，仅供审核和后端定位使用",
  "regionalScope": "national",
  "retrievedAt": "YYYY-MM-DD",
  "enteredBy": "legal_editor_id",
  "reviewedBy": "legal_reviewer_id",
  "reviewedAt": "YYYY-MM-DD"
}
```



终点映射单独转换，不把同一法条原文复制进每个终点：



```JSON
{
  "treeId": "pregnancy_pay_cut",
  "terminalId": "PA",
  "requiredLegalBasisKeys": ["female_worker_protection_5"],
  "conditionalLegalBasisRules": [
    {
      "legalBasisKey": "women_rights_48",
      "when": {
        "any": [
          { "node": "P6", "value": "salary_reduced" },
          { "node": "P6", "value": "both" }
        ]
      }
    }
  ],
  "displayOrder": ["female_worker_protection_5", "women_rights_48"],
  "version": "1.0.0",
  "status": "reviewing"
}
```



转换规则：



- 法条记录与终点映射分别版本化；

- `treeIds/terminalIds` 如需用于检索，应由映射表反向生成，不由开发手填第二份关系；

- JSON 字段值必须忠实于法学材料，不允许清洗时改变法条文字；

- 转换结果生成差异报告，方便法学同学核对是否有丢字、错序或条件变化。

#### **11.10.5 开发工作三：建立索引与实现查询**



后端至少建立：



- 法条记录的 `legalBasisKey + version` 唯一索引；

- 终点映射的 `treeId + terminalId + version` 唯一索引；

- 从 `legalBasisKey` 反查引用终点的多对多索引；

- `status/effectiveDate/regionalScope` 查询索引，防止返回未发布、未生效或地区不匹配的依据。

查询函数建议：



```JavaScript
resolveLegalBasis({
  treeId,
  treeVersion,
  terminalId,
  canonicalNodeAnswers,
  canonicalFlags,
  userRegion,
  decisionDate
});
```



查询顺序：



1. 加载当前树版本对应的已发布终点映射；

2. 先加入全部必选 `legalBasisKeys`；

3. 使用 `canonicalNodeAnswers + canonicalFlags` 按 10\.5 语义计算条件依据；

4. 合并、去重并按 `displayOrder` 排序；

5. 批量读取对应的 `published` 法条记录；

6. 校验生效日期、地区和版本；

7. 返回 `lawName/article/displayText/fullText/officialUrl/effectiveDate/retrievedAt`；

8. 任一必选依据缺失或不可用时阻断裁决包生成并记录配置错误，不能静默省略。

同一法条被多个场景或终点引用时只存一份原文。`applicabilityNote` 只用于后端规则定位、审核报告和排错，不直接展示给用户；如需说明与当前路径的关系，应使用单独且明确标注为说明文字的字段。



#### **11.10.6 开发工作四：提交法学核验**



开发完成配置、索引和查询逻辑后，应按每个正式终点及其相关条件组合生成法律依据区快照，交回法学同学核对：



- `displayText/fullText` 是否与材料一逐字一致；

- 必选法条是否在每条相关路径下都出现；

- 条件法条是否只在条件满足时出现；

- 多个条件同时满足时是否正确去重和排序；

- 法条展示顺序是否符合材料二；

- `displayText` 的截取或折叠是否影响原文含义；

- 官方链接、文号、生效日期、地区和状态是否正确；

- 不应展示的依据是否确实没有出现；

- OOS 结果是否未返回本项目法律依据；

- 历史版本是否仍能读取当时的法条原文快照。

法学同学确认无误并填写审核记录后，开发才能将法条记录和终点映射从 `reviewing` 改为 `published`。任何原文、条件、顺序或映射修改都必须提升相应版本，重新生成快照并复核。



#### **11.10.7 一句话职责边界**



|角色|交付内容|
|---|---|
|法学同学|法律依据条目表、终点法律依据映射表，共 2 份材料|
|开发同学|校验法学材料、转换 JSON、建立索引并实现查询、提交法学核验，共 4 项工作|



**法学同学不写 JSON、不实现查询；开发同学不补写法条原文、不自行建立终点映射。最终发布物必须保证法学条目表、终点映射、后端 JSON 和裁决包快照四方一致。**



## **12. 文书审核清单**



发布前逐份确认：



* [ ] 文书只映射到经过审核的终点；

* [ ] 标题、收件人和请求事项匹配当前阶段；

* [ ] 必填字段足以生成完整成品；

* [ ] 选填字段缺失时正文仍通顺；

* [ ] 条件段落不会同时出现互相矛盾的事实；

* [ ] 未补写用户没有确认的人名、日期、金额和行为；

* [ ] 法律名称、条款号和官方来源准确；

* [ ] 时效表述包含必要例外和核实提醒；

* [ ] 不包含胜诉保证和绝对违法结论；

* [ ] 证据建议不鼓励违法取证；

* [ ] OOS 终点没有关联文书；

* [ ] 示例数据可以生成可直接阅读的成品；

* [ ] 模板版本、审核人和审核日期完整；

* [ ] 前端渲染结果与法学审核稿一致。

## **13. 首版完成标准**



首版必须同时满足：



1. 五棵树全部节点、选项、下一跳和终点完整；

2. 20 个正式终点和 OOS 分支均可到达；

3. 14 类文书模板均形成完整模板包；

4. 法律依据库只收录与场景和终点直接相关、会展示在裁决包中的法条原文；

5. 每个正式终点均配置经审核的 `legalBasisKeys`，并完成法律依据区快照验收；

6. 每个非 OOS 终点都有明确文书白名单；

7. 每棵树不少于 20 条测试用例，五棵树合计不少于 100 条；

8. 五棵树分别完成法学逐路径审核；

9. 后端能根据合法 `path + answers` 独立复算终点并生成成品文书；

10. 必填字段缺失时返回字段列表，不生成半成品；

11. 前端只展示、复制和下载后端返回的成品文书；

12. 任一场景未通过审核时，不得以基础指引或占位入口替代完整能力发布。
