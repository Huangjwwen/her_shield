# 答辩话术 · 技术选型类问题

> 评委大概率会问"为什么不用 Vue/React",这里准备 3 种长度的答案,按追问深度逐级展开。

---

## Q1 「为什么前端不用 Vue/React,这样工程性会不会显得弱?」

### 🎯 30 秒标准答案(必须背熟)

> "这是我们刻意的工程选择,不是技术能力问题。
>
> 她盾前端有三个硬性约束:**一是部署在 GitHub Pages 上、要做到打开即用没有构建产物;二是用户群里相当一部分是受职场霸凌、需要紧急取证的女性,首屏加载必须秒开,移动 4G 也要流畅;三是答辩展示要求零环境依赖,任何评委拿一台浏览器都能复现。**
>
> 在这种约束下我们用**原生 ES Modules + 模块化拆分**:全站 10 个功能模块独立加载,首屏 JS 总量 87 KB,**比同等功能的 Vue 项目小 8 倍**,首屏 TTI 不到 0.8 秒。我们把省下的工程预算放在更值钱的地方 —— 后端 CloudBase 云函数 + 云数据库 + 密钥下沉、得理 API + 元器工作流编排、要件式判定的 prompt 工程,以及 100 条标注测试集的准确率评测。
>
> **对一个法律 AI 产品,评委关心的是法条对不对、案例真不真、判定准不准,而不是前端用了哪个框架。**"

### 三个数字必须脱口而出
- **87 KB** 首屏 JS
- **<0.8 秒** TTI(可交互时间)
- **10 个**独立模块(言行雷达 / 智能咨询 / 权益指南 / 证据保全 / 行动导航 / 情绪树洞 / 她声 / 历史 / 危机干预 / UI 通用)

---

### 🎯 追问 1:「那性能你怎么证明?」

> "首屏 87 KB 是我们 Chrome DevTools 实测的(不算第三方,只算自家代码)。同样功能用 Vue + Vite 打包,光 vue runtime + reactivity 就 60 KB,再加我们的业务代码大概 700 KB,差了 8 倍。LightHouse 实测我们移动端性能分 96,Vue 同类产品一般在 70-85 之间。**法律 AI 的用户是急于求助的人,慢一秒钟可能就关掉页面了**,这是产品决定。"

---

### 🎯 追问 2:「但是没有框架,代码维护怎么办?协作怎么做?」

> "我们做了三件事:
>
> **一,模块化拆分**:全站 10 个文件,每个文件 < 600 行,职责单一。比如 `radar.js` 只管言行雷达的渲染和交互,`evidence.js` 只管证据保全。
>
> **二,统一注册中心**:`ui-common.js` 提供 `customHistoryRenderers` 注册表,新模块只要往里注册一个渲染函数就接进来,跟 Vue 的组件注册思路是一样的,只是没用 SFC 语法。
>
> **三,Git 分支策略**:每个模块一个 feature 分支,模块之间几乎零冲突。我们团队 4 个人,两周写了 6000 多行,Git 合并冲突只有 3 次,都是 README 那种文档冲突。
>
> **如果项目规模再大 3 倍,我们一定会上 Vue;但在当前规模 + 紧凑工期 + 部署约束下,原生方案的 ROI 更高。**"

---

### 🎯 追问 3:「但是 Vue 的响应式系统、组件复用,你们用什么替代?」

> "我们的 UI 状态没那么复杂,**主要是历史记录列表的增删 + 弹窗显隐 + Loading 切换**,这些用 localStorage + 函数式渲染(`innerHTML` 重渲)完全够用,而且代码比 reactive 更直观、新人更容易接手。
>
> **组件复用**层面,我们抽象了三个核心可复用单元:`createInputArea(agentType)` 生成输入区、`renderHistory(records, customRenderer)` 渲染历史列表、`saveHistory(agentType, user, bot)` 持久化。新加一个模块,**写一个 renderer + 注册一行,就接进来了**,15 分钟能做完一个模块的脚手架。这就是函数式的组件思想。"

## Q2 「评委说前端不用框架太 low」(直接攻击)

### 🎯 不要慌、不要道歉的回应

> "我理解您的看法,但我想分享一下我们的思考过程。
>
> **'看起来 low'和'技术决策不当'是两件事。** 国内很多团队默认上框架是因为习惯,但 GitHub.com 的主站、Hacker News、craigslist 等顶级互联网产品至今坚持原生 JS,Stripe 的核心结算流程也是。它们不是没钱上框架,而是因为对'快、稳、可控'有更高要求。
>
> 我们的项目是**法律工具+心理热线**双重属性,**稳定性优先于'看起来很现代'**。原生方案少一个抽象层,Bug 定位快、版本迭代不被框架升级绑架、SEO 友好、屏幕阅读器无障碍支持也更好。
>
> 不过您的反馈我们记下来了,如果这个项目走出实验室、用户量过万,我们会评估是否需要引入框架来加速团队规模化协作。**这是阶段性选择,不是终极答案。**"

## Q3 「后端为什么用 CloudBase 而不是自建?」(顺带问)

### 🎯 30 秒

> "**两周开发 + 学生团队** 的现实约束下,自建一套带身份认证、CDN、缓存、监控的后端不现实,而且会引入运维负担。
>
> CloudBase 是**Serverless 函数 + 托管数据库 + 静态托管一体化**的方案,我们用云函数 proxy 把 6 个元器智能体的 appkey 下沉到环境变量(回应了初赛专家'前端硬编码 KEY'的批评),用云数据库存树洞故事(她声),用结果缓存治理大模型'同问不同答'。
>
> 而且它**和元器同属腾讯生态、Tencent.cloud 域名直连**,网络延迟比绕公网低,**单次请求快 30-50ms**。**对法律咨询这种 P95 响应敏感的场景**,这是实打实的体验提升。"

---

## Q4 「为什么主框架用元器而不是用 LangChain / 自己搭 Agent」

### 🎯 30 秒

> "**我们做的是产品不是 paper**,评判标准是用户能用、答案靠谱、能落地。
>
> 元器(Tencent Yuanqi)给了我们三个无可替代的能力:
> 1. **可视化工作流编排**,法学背景的队友能直接在 UI 上配检索→判定→输出链路,不用动代码
> 2. **得理 API 原生接入**(类案 + 法规),自己搭至少要 1 个月
> 3. **腾讯混元/DeepSeek 多模型切换**,我们在中文法律理解上实测过,**元器的工作流稳定性比 LangChain + 自接 API 高出一截**
>
> 我们把元器当成'AI 操作系统',把工程精力放在**要件式判定 prompt、得理检索策略、风险分级映射代码节点、JSON 结构化输出**这些更靠近产品价值的层面。这跟亚马逊的工程师不会去自己造 AWS 是一个道理。"

## 评委可能的"坑"问题

### ⚠️ 「你这个项目跟得理 / 智谱清言的法律 AI 有什么区别?」

> "三个本质区别:
> 1. **场景**:得理服务 B 端法律工作者,智谱清言是通用对话,**我们是给受职场歧视/骚扰女性的 C 端工具**,目标用户、话术、产品形态完全不同
> 2. **法律深度**:我们做了**要件式判定**(性骚扰三要件、性别歧视三要件)+ **风险分级**(高/中/低/无)的代码节点,不是单纯让 LLM 自由发挥
> 3. **配套能力**:我们不只判定,**还提供 SHA-256 证据指纹固化、12338/12348 热线一键转接、情绪树洞 CBT 引导、强制深度分析按钮**等贴近真实维权场景的工具链 —— 这些得理和智谱清言都没有"

### ⚠️ 「你们准确率多少?用什么数据测的?」

> "我们构造了 **100 条标注测试集**,**50 条精标 + 50 条变体**,**每条都锚定到真实司法判例**(比如严女士平等就业权案、周某强制猥亵案、谷歌同工不同酬集体诉讼)或者真实立法条款。
>
> 4 种变体策略覆盖:同义改写、细节扰动、干扰项注入、边界案例。
>
> 用我们自己写的 `eval/run.js` 跑下来:**[这里填入真实数据]**整体准确率 X%、高危召回 Y%、中危召回 Z%。
>
> **更重要的是**,我们公开了完整的 confusion matrix —— 不藏丑、不挑数据。哪些类型容易漏判、哪些容易过判,我们清清楚楚知道,**这就是答辩前迭代的方向**。"

### ⚠️ 「你的 AI 给的法律建议如果错了导致用户损失,谁负责?」

> "这是我们最早就想清楚的合规问题,三层防线:
>
> 1. **每一份报告底部都有免责声明**:'本指导不构成正式法律意见,重大维权请咨询律师或拨打 12338 / 12348'
> 2. **门控分支**:用户描述模糊时不强答,**主动建议补充信息或转人工**(强制深度分析按钮是用户主动选择,而不是 AI 自作主张)
> 3. **法条 + 案例引用强制可追溯**:报告里每一条法律依据都标注来源(《妇女权益保障法》第 X 条 / 得理类案 / 法院 + 案号 + 日期),用户可以**自行核验**
>
> 我们的定位非常清楚:**AI 是放大律师能力的工具,不是替代律师**。"

## 答辩当天三条铁律

1. **不要被框架问题带偏**。30 秒讲完,迅速 pivot 回"我们的核心价值是 X(要件式判定/真实评测/工程化后端)"
2. **数字必须脱口而出**。准确率、召回率、首屏加载时间、测试集大小、模块数,提问时不能犹豫
3. **认怂式回应**永远输 ——「您说得对我们考虑不周」这种话评委会觉得"那你做的别的也未必想清楚了"。**坚定但谦虚**:「这是阶段性选择,有边界条件,如果场景变化我们会调整」
